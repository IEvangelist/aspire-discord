Building Aspirey Bot

A Discord assistant on Aspire, the GitHub Copilot SDK, and Azure OpenAI

What it does, how it evolved, and where it stands today.

Start presentation
0:00-0:01. Welcome. This is the story of how I built a Discord assistant: what it can do, how it grew over six weeks, and where it stands today. Three technologies run through all of it. Aspire runs it, the GitHub Copilot SDK drives the agent, and Azure OpenAI supplies the models. Advance with Start presentation.

0:01-0:02. The whole product in four steps. Each step is a bigger promise, and each one needs a new place to find the truth. It answers from the docs and the API surface. It looks things up on GitHub, read-only. It reads the room: the thread, the reply, the screenshot. And it takes action, but only by drafting an issue that a person approves. The next four slides show each step as a short chat. They are staged examples. If you are demoing live, run them in Discord instead.

3 · It reads the room

Reply to a screenshot. It reads that too.

  2. Reads the screenshotIt looks at the image, not just the text.

0:04-0:05. Scene three. It reads the room. Reply to someone's message that has a screenshot, mention the bot, and it uses the reply and the image as context. That context is redacted, bounded, and treated as data: it can inform the answer, but it can never give the bot instructions. The other person and the screenshot are invented. 4 · It takes action

Say “turn this into an issue.” You click to approve.

  1. Written from the threadTitle, body, and sourced investigation.
  2. Repository inferredIt asks only when it cannot tell.
  3. Nothing posts until you clickOnly the requester can approve.
0:05-0:07. Scene four, the one that raises the stakes. Say turn this into an issue and the bot writes a title and body from the conversation, picks the repository when it is obvious, and posts a preview. Nothing is posted until the requester clicks Create issue. Click once to reveal the preview. LIVE OPTION: click Cancel, never Create issue. The bot replies that the draft was cancelled and nothing was published.

The rules it never breaks

The model proposes. Code decides.

No source, no answer

A factual reply must cite something a tool returned.

No click, no write

Only the requester can approve an issue.

Only the list

Allow-listed people, rate-limited. Open access is an explicit opt-in.

It can draft an issue. It cannot file one.

0:07-0:08. Three rules hold all of that together. No source, no answer: a factual reply has to cite something a tool returned, or it becomes a refusal. No click, no write: only the requester can approve an issue. Only the list: access is allow-listed and rate-limited, and opening it up takes an explicit opt-in. The line to remember is that the model can draft an issue, but it cannot file one. The rest of the talk is how those rules came to exist.

Aug 17 · Chapter 1 · It answers

It started as a docs bot that knew its limits.

  1. A hard refusalIf the docs do not cover it, say so.
  2. Three days later: too hardIt refused an EF Core question the docs covered.
  3. So I rebalancedA looser prompt, and an eval harness.
  1. C# AppHost
  3. Qdrant
  4. Ingestion worker
  5. Discord bot
0:09-0:11. August 17: a docs bot. One C# AppHost started Qdrant, an ingestion worker, and the bot, and it answered only from the official docs, with citations and a hard refusal. That refusal was the best feature, until August 20, when it refused a question about EF Core migrations that the docs clearly covered. My prompt was too strict. I loosened it and added an answer-quality eval harness so quality stays locked in. Lesson to carry forward: refusals can be wrong too.

Aug 20 · Chapter 2 · It finds more truth

Every gap became a tool.

  • One search missed multi-part questions.An agent loop that plans, searches, and reads again.
  • It could not answer about real APIs.A Roslyn-built API index and search_api.
  • The real answer lived in an issue thread.Live GitHub code and issue search.
  • The agent was a black box.OpenTelemetry traces in the Aspire dashboard.
0:11-0:12. August 20 was the big day. Each gap became a tool. One search was not enough for multi-part questions, so the bot became an agent loop that plans, searches, reads, and searches again. It could not answer questions about real APIs, so a Roslyn parser built an API index. A question about running a command inside a container had its real answer in an open issue thread, so I added live GitHub search. And the agent was a black box, so I added OpenTelemetry GenAI traces that light up the Aspire dashboard. OPTIONAL: if your local AppHost is running, open its dashboard's GenAI view for the last request.

Aug 24 · Chapter 3 · It’s rebuilt

I replaced my agent plumbing with the Copilot SDK.

The SDK gives me sessions, streaming, and tool calls. I start it with nothing: only the tools I register.

0:12-0:13. August 24: I replaced my agent plumbing with the official GitHub Copilot SDK. Until then I had my own device-flow sign-in, token exchange, and tool loop. On August 18 the Aspire dashboard even showed the sign-in code through the interaction service. The SDK gives me sessions, streaming, and tool calling. What I kept is control. Step through the excerpt: the client starts in empty mode, only my custom tools are available, and config discovery, file hooks, host Git, the session store, and skills are all off.

Aug 27 · Chapter 3 · It’s rebuilt

I rewrote it in TypeScript to see if Aspire could handle it.

It could. A TypeScript AppHost runs a Qdrant container, a .NET worker, and a Node.js bot.

0:13-0:15. August 27: I rewrote the bot and the AppHost in TypeScript. The reason is simple. I wanted to know whether Aspire could handle it. The AppHost models a Qdrant container, a .NET ingestion project, and a Node.js bot, in one file, in TypeScript. Step through the three parts: the store, the .NET worker, and the bot with its dependency on the worker. It could handle it. Same dashboard, same health checks, same one command.

Aug 28 · Chapter 4 · It ships

Qdrant did not survive the move to Azure.

  • On my laptop

    Qdrant runs as a container resource in the AppHost, with a data volume.

  • In Azure

    Production uses Azure AI Search, a managed service.

  1. Qdrant on Container Apps
  3. NFS storage: unsupported
  5. Azure AI Search

One retrieval interface, two stores. A setting chooses which: VECTOR_STORE_PROVIDER.

0:15-0:16. August 28: the move to Azure Container Apps. My first deployment ran Qdrant on NFS-backed storage, and that turned out to be unsupported, so production moved to Azure AI Search. Locally, Qdrant is still one line in the AppHost. The retrieval code does not care: one interface, two stores, and a single setting chooses between them.

Aug 28 · Chapter 4 · It ships

In Azure, there are no API keys.

A token provider replaces the key, for chat and for embeddings. In Azure, the app’s managed identity gets the token, and the SDK keeps the same loop and tools.

0:16-0:17. In Azure there are no API keys. The Copilot SDK lets you bring your own model provider, and I give it a token provider instead of a key. In Azure that resolves to the container app's managed identity. On a laptop it resolves to my own az login, and the SDK's default models come from GitHub Copilot. The embeddings client uses the same token provider. Same agent loop, same tools; only the provider block changes. That is also why production does not need a personal Copilot login.

Aug 28–31 · Chapter 4 · It ships

Deploys had to be boring.

aspire deploy runs a pipeline I own. Nothing cuts over until the new slot passes its live checks.

0:17-0:19. Deploys had to be boring. aspire deploy runs a pipeline I own. Preflight checks for a clean commit and valid Azure access. Images are tagged by Git SHA, so every deployment is immutable. A new slot starts with Discord disabled and must pass live checks against GitHub, MCP, and storage. Only then does one Discord session cut over, and if that fails the previous slot returns. If you are running long, compress this to one sentence: nothing cuts over until the new slot proves itself.

Aug 31–Sep 1 · Chapter 5 · It sees and listens

Then it learned to see, listen, and explain itself.

  • Images

    It reads the screenshot you attach.

  • Mention-only

    No slash command. Mention it, then reply to keep going.

  • Traces

  • Live config

0:19-0:20. Four quick upgrades in one week. It reads images and screenshots. It became mention-only: no slash command, and replies to the bot keep the conversation going. Production got traces: one trace ID from the Discord message to the model call, in the Aspire dashboard locally and in Application Insights in Azure. And runtime configuration is live, so I can change who may use it without a deploy.

Sep 23 · Chapter 6 · It acts

Then I let it act, carefully.

No publish tool. No approve tool. The signing key never leaves Key Vault.

0:20-0:22. September 23: I let it act. This is the most important design decision in the project. The model can call prepare_issue_draft, but there is no publish tool and no approve tool. The draft becomes a durable preview with the exact title and body. Only the requester can approve it, with an authenticated button. Deterministic code re-checks the user, server, repository, and expiry. Key Vault signs the GitHub App's token so the key never leaves, and a one-repository token creates the issue. The gate boxes are code, not prompts.

Sep 23–28 · Chapter 6 · It acts

A regex missed the word “test”.

Sep 28: drafts now get an AI-written title and body, plus sourced investigation.

0:22-0:23. A real failure. Someone asked the bot to create a test issue and it was ignored, because my regular expression did not allow the word test. I patched it once, then removed the whole approach. Now one conversation agent sees typed tools and chooses which to call, including asking a clarifying question or cancelling. Code still validates every argument. On September 28 drafts got smarter too: the title and body are written from the conversation, with sourced investigation.

0:23-0:25. Where it stands today, on one page. Discord mentions reach the Node.js bot. The bot runs a Copilot SDK agent session that calls Azure OpenAI. Where it stands

What I’d tell myself on Aug 17.

  • It refused what the docs covered.

    Test for over-refusal, not just leaks.

  • A regex missed the word “test”.

    Let the model pick typed tools.

  • Agents are hard to debug.

    Trace every request from day one.

  • Acting raised the stakes.

    Keep the boundary in code, not the prompt.

0:25-0:28. Four lessons, each from a real incident. Test for over-refusal, not just leaks: my first refusal rule was too strict. Let the model pick typed tools instead of matching keywords. Trace every request from day one, because that is what made the agent debuggable. And once it can act, keep the boundary in code, not in the prompt: a prompt is not a policy. If there is time, ask the audience which of these they have already hit in their own agents.

The AppHost resource graph.

Locally, Qdrant stands in for Azure AI Search. Ollama is an opt-in local model.

Appendix only. The AppHost starts Qdrant, ingestion, and the bot. Ingestion publishes indexes and the bot waits for it. Secrets stay in Aspire's secret store and reach the bot as environment values. Both services send OTLP to the dashboard. Configuration selects the provider; the bot code stays the same.

One request through the agent.

Authorization, limits, and input rules run before any model call.

Appendix only. Before any model call, deterministic code checks authorization, rate limits, duplicate messages, and input rules. Context from threads, replies, and attachments is redacted and bounded. A fresh agent session prompts Azure OpenAI, which chooses tools and reads their results. The answer gate requires a citation that a tool actually returned; otherwise the bot refuses. The progress reply is edited in place into the answer, with its sources right under it.

Ingestion builds memory off the hot path.

A failed refresh is rolled back. The last usable index stays online.

Appendix only. Memory is built off the hot path by a .NET worker. It reads published docs and a pinned commit of the Aspire source, parses the public API with Roslyn, chunks the content, and embeds it with Azure OpenAI. Results go to staged index generations. One alias swap publishes docs and API together so the bot never sees a half-built pair. If anything fails, the build is rolled back and the last good index stays online.

One trace from Discord message to model call.

One trace ID across the dashboard and Application Insights.

Appendix only. Each Discord request is the root span and records an outcome such as answered, not grounded, rate limited, or failed. The agent span is its child, with GenAI attributes and duration, and the embedding spans add token usage. Tool calls create embedding and search spans. In development the SDK runtime also exports model spans over OTLP, and the bot passes the active trace context to the SDK so those spans join the same trace. Locally it lands in the Aspire dashboard; in Azure it lands in Application Insights.

Same code. Different telemetry sink.

When Aspire runs the bot, OTLP settings are present and traces land in the dashboard. In Azure, an Application Insights connection string selects Azure Monitor.

Appendix only. The bot picks its telemetry sink from the environment. When Aspire runs it, OTLP settings are present, so spans and metrics go to the dashboard. In Azure, an Application Insights connection string selects Azure Monitor, authenticated with managed identity. With neither, telemetry is off.

Custom steps join the Aspire pipeline.

dependsOn orders the steps. requiredBy puts the blue/green step inside aspire deploy.

Appendix only. A custom step is added to the Aspire pipeline and wired with dependsOn and requiredBy, so aspire deploy runs preflight first and the blue/green step as part of the deploy. Aspire owns the entry point, the step order, and cancellation. The step itself delegates the Azure operations to a reviewed script.

Every capability is a typed tool.

The model can request a report. It cannot request ten years of history. Invalid calls fail before any request is made.

Appendix only. A tool is a zod schema, a handler, and a budget. This schema is the contract for the GitHub activity report: a fixed set of report kinds, a validated username, ISO dates, and a rule that the range is at most 366 days. An invalid call is rejected before any request is made. Tool results come back as untrusted data with citations.

GitHub access is read-only, enforced twice.

  • The serverA read-only header and an exact tool allow-list.
  • The applicationA repository allow-list, rejected scope expansion, and bounded queries.
  • Separate from issue creationIssues use a different GitHub App and a different code path.
Appendix only. GitHub access is read-only by construction: the server enforces a read-only header and an exact tool list, and the application enforces a repository allow-list and bounded queries. Issue creation uses a separate GitHub App.

The Azure footprint is keyless.

  • Container Apps and RegistryTwo slots, one active Discord session, Git-SHA image tags.
  • Azure OpenAI and AI SearchChat and embedding deployments, versioned indexes behind aliases.
  • App Configuration and Key VaultLive policy, and signing without exposing the key.
  • Application Insights and storageLogs, traces, metrics, and durable issue drafts.
Appendix only. The Azure footprint, deliberately keyless: a managed identity with narrow role assignments reaches every service. Resource names are intentionally omitted from this public deck.
